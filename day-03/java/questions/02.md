# Q02 — Optional lookups on your Day 1 User repository

**Continuation from Day 1 Q01** — reuse `Repository<User>`, `User`, and `Identifiable`.

Your repository already finds users by id. Wrap those lookups with `Optional` so callers never chain null checks.

## What changes from Day 1

Add one optional field to `User`:

- `String email` — may be `null` when unknown

Keep `findById(Long id)` returning `Optional<User>` (align with the Day 1 spec if your implementation still returns bare `User` / `null`).

## Requirements

1. Implement `UserService` backed by `Repository<User>`:
   - `Optional<User> findUser(Long id)`
   - `Optional<String> findEmail(Long id)` — empty if user missing **or** email is null
   - `String findNameOr(Long id, String defaultName)` — use `orElse` / `orElseGet`
   - `Optional<String> findVerifiedEmail(Long id, Predicate<String> isValid)` — present only when email exists **and** predicate passes (`filter`, `flatMap`)
2. Demo three cases in `main`: user with email, user without email, unknown id.

## Constraints

- Service methods that return `Optional<...>` must not return `null`.
- Use `Optional` API (`map`, `flatMap`, `filter`, `orElse`) — no `if (user != null && user.getEmail() != null)` in the service.
- `Predicate<String>` from `java.util.function`.

## Expected behavior

```text
users.save(new User(1L, "Ada", "ada@example.com"));
users.save(new User(2L, "Bob", null));

findNameOr(1L, "Guest")                         → "Ada"
findNameOr(99L, "Guest")                        → "Guest"
findEmail(1L)                                   → Optional["ada@example.com"]
findEmail(2L)                                   → Optional.empty
findVerifiedEmail(1L, e -> e.contains("@"))      → Optional["ada@example.com"]
findVerifiedEmail(2L, e -> true)                → Optional.empty
```
