# Q01 — Virtual threads: many blocking tasks

**Virtual threads** (Java 21) are lightweight threads meant for **I/O-heavy** work. The JVM mounts many virtual threads onto a small pool of platform threads, so blocking one virtual thread does not waste an OS thread.

## Scenario

A log-ingestion tool must process thousands of small jobs. Each job simulates network latency with `Thread.sleep` (50–100 ms). Platform-thread pools choke at a few hundred tasks; virtual threads handle far more with simpler code.

## Requirements

1. Define `record IngestJob(int id, int delayMs)` and `record IngestResult(int id, boolean ok)`.
2. Implement `IngestResult process(IngestJob job)`:
   - Reject `delayMs < 0` with `IllegalArgumentException`
   - `Thread.sleep(job.delayMs())`, then return `new IngestResult(job.id(), true)`
3. Implement `List<IngestResult> processAll(List<IngestJob> jobs)` using:
   - `Executors.newVirtualThreadPerTaskExecutor()` inside **try-with-resources**
   - One submitted task per job; collect results in **input order** (preserve job list order in the returned list)
4. Demo in `main` with at least **1_000** jobs (mixed delays). Print count of successful results and total elapsed time.

## Constraints

- Java 21+ (`--enable-preview` not required for virtual threads in 21 final).
- Use a **virtual-thread executor** — not `Executors.newFixedThreadPool` for this exercise.
- Shut down the executor via try-with-resources (or explicit `close()`).
- Do not drop or reorder results relative to the input list.

## Expected behavior

```text
jobs = 1_000 IngestJob instances with delayMs in [50, 100]

processAll(jobs).size() == 1_000
all results have ok == true

// completes in roughly ~100–200 ms wall time (parallel virtual threads),
// not ~50–100 seconds (sequential)
```

## Hint

`try (var executor = Executors.newVirtualThreadPerTaskExecutor()) { ... }` — submit with `executor.submit(() -> ...)`, store `Future`s in a list, then `get()` in order.
