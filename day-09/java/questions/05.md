# Q05 — Token sum: exceptions as control flow

Most tokens are words like `item-42`; every 20th is a number. Summing 400k tokens takes **~300+ ms**. The loop looks innocent — VisualVM will show where the time really goes.

## Starter code

```java
public class TokenSum {
    static long total(String[] tokens) {
        long sum = 0;
        for (String token : tokens) {
            try {
                sum += Integer.parseInt(token);
            } catch (NumberFormatException ex) {
                // not a number — skip
            }
        }
        return sum;
    }

    public static void main(String[] args) {
        int n = 400_000;
        String[] tokens = new String[n];
        for (int i = 0; i < n; i++) {
            tokens[i] = i % 20 == 0 ? Integer.toString(i) : "item-" + (i % 100);
        }
        long t = System.nanoTime();
        long sum = total(tokens);
        System.out.println("sum=" + sum + " ms=" + (System.nanoTime() - t) / 1_000_000);
    }
}
```

## Your task

1. Run and profile with VisualVM Sampler.
2. Find **~380k** `NumberFormatException` constructions per run in the hot path (or time in `Integer.parseInt` + exception machinery).
3. Fix: **check before parse** — only call `parseInt` when the token is numeric.
4. Keep `sum=3999800000`.

## What VisualVM should show

- `NumberFormatException.<init>` or `Integer.parseInt` dominating
- Exception count huge compared to successful parses

## Fix hint (after you profile)

Small `isNumeric(token)` helper, or `Character.isDigit` on first char before parsing.

## Expected behavior

```text
sum=3999800000
// after fix: ms drops to roughly 10–30
```
