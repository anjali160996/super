# Q03 — Report archive: GC eating your time

Rendering 15,000 reports finishes in ~150 ms, but the JVM holds **60+ MB** heap and VisualVM shows heavy **GC** activity. The CPU sampler alone is not enough — use **Monitor** + **Heap dump**.

## Starter code

```java
public class ReportArchive {
    static class ReportService {
        final StringBuilder archive = new StringBuilder();

        String render(int requestId) {
            String body = "report=" + requestId + " status=ok " + "x".repeat(4096);
            archive.append(body);
            archive.append('\n');
            return body;
        }
    }

    public static void main(String[] args) {
        ReportService svc = new ReportService();
        int n = 15_000;
        long t = System.nanoTime();
        int chars = 0;
        for (int i = 0; i < n; i++) {
            chars += svc.render(i).length();
        }
        System.gc();
        long usedMb = (Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory()) / 1024 / 1024;
        System.out.println("chars=" + chars
                + " archiveLen=" + svc.archive.length()
                + " usedMB=" + usedMb
                + " ms=" + (System.nanoTime() - t) / 1_000_000);
    }
}
```

## Your task

1. Run with `-Xmx512m` and attach VisualVM.
2. **Monitor** → watch heap climb; note GC spikes.
3. **Heap dump** → find what `ReportService.archive` retains (millions of chars).
4. Fix retention: archive only what you need (e.g. request id per line), not the full 4k body.

## What VisualVM should show

- Large `char[]` / `String` retained by `StringBuilder` inside `ReportService`
- `archiveLen` in the tens of millions after the run

## Fix hint (after you profile)

`archive` should store a small summary per report (id + newline), not the full padded body.

## Expected behavior

```text
chars=61773890
// after fix: usedMB roughly 1–5, archiveLen ~75_000, ms similar or lower
```
