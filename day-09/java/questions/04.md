# Q04 — Latency histogram: boxing and hashing

You fold 3M latency samples into 64 buckets. Correct answer, but **~90 ms**. Sampler shows time in `HashMap.merge`, `Integer`, and allocation — not in the arithmetic.

## Starter code

```java
import java.util.HashMap;
import java.util.Map;

public class LatencyFold {
    static long checksum(int[] samples) {
        Map<Integer, Long> hist = new HashMap<>();
        for (int sample : samples) {
            hist.merge(Math.floorMod(sample, 64), 1L, Long::sum);
        }
        long folded = 0;
        for (var entry : hist.entrySet()) {
            folded += (long) entry.getKey() * entry.getValue();
        }
        return folded;
    }

    public static void main(String[] args) {
        int[] samples = new int[3_000_000];
        for (int i = 0; i < samples.length; i++) {
            samples[i] = i * 17;
        }
        long t = System.nanoTime();
        long folded = checksum(samples);
        System.out.println("folded=" + folded + " ms=" + (System.nanoTime() - t) / 1_000_000);
    }
}
```

## Your task

1. Profile with VisualVM Sampler (CPU + Allocations if available).
2. Confirm hot path: `HashMap` operations and boxed `Integer` keys on every sample.
3. Replace the map with a **fixed `long[64]`** histogram — same formula, no boxing.
4. Verify `folded=94500000` unchanged.

## What VisualVM should show

- `HashMap.merge`, `Integer.valueOf`, or `HashMap.put` near top of hot methods
- Millions of short-lived objects in allocation view

## Fix hint (after you profile)

`long[] hist = new long[64];` then `hist[Math.floorMod(sample, 64)]++;`

## Expected behavior

```text
folded=94500000
// after fix: ms drops to roughly 10–25
```
