# Q02 — Sealed types + pattern matching for payment results

**Sealed classes** (Java 17) restrict who may extend a type. Combined with **pattern matching for `switch`**, you get exhaustive, readable branching without long `if-else` chains.

## Requirements

1. Declare a **sealed interface** `PaymentResult` with exactly three permitted implementations:
   - `record Approved(String transactionId, double amount)`
   - `record Declined(String reason)`
   - `record Pending(String reference)`
2. Implement `String describe(PaymentResult result)` using a **`switch` expression** with pattern matching (not `instanceof` + cast chains).
3. The `switch` must be **exhaustive** — compiler should accept it without a `default` that hides missing cases.
4. Demo in `main` with one instance of each variant; print the description string.

## Constraints

- Java 17+ syntax (`sealed`, `permits`, record implementers).
- Use a `switch` **expression** that returns a `String` (or assign its value to a variable).
- Do not use reflection or string-based type names.

## Expected behavior

```text
describe(new Approved("TXN-9", 1500.0))
  → "Approved TXN-9 for 1500.00"

describe(new Declined("Insufficient funds"))
  → "Declined: Insufficient funds"

describe(new Pending("REF-42"))
  → "Pending reference REF-42"
```
